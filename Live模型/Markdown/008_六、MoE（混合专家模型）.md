### 一、MoE 基础架构、路由设计与大模型缩放（Scaling）效率

#### 1. 项目中 Dense 模型与 MoE 模型在推理实现上有哪些差异？Expert Parallelism（EP）是如何实现的？

- Dense 模型和 MoE 模型在推理实现上的核心差异在于 **计算路径是否数据依赖**。Dense 模型每一层对所有 token 执行完全相同的计算（相同的 FFN 权重），计算图是静态的，batch 内所有样本走同一条路径，天然适合大 GEMM 和 Tensor Core。MoE 模型则引入了 **Router（门控网络）**，每个 token 根据 router 的输出被分配到不同的 Expert（通常 top-2），这意味着 **不同 token 走不同的计算路径**，计算图变成了动态的、稀疏的。推理实现上的主要挑战有三个：第一，**负载不均衡**——热门 Expert 可能收到 80% 的 token，冷门 Expert 几乎空闲；第二，**通信开销**——Expert 分布在不同 GPU 上时，token 需要 all-to-all 通信路由到对应 Expert；第三，**显存占用**——所有 Expert 的权重都要存储（即使大部分时间只用其中几个）。Expert Parallelism 的实现核心是 **将不同 Expert 的权重放在不同 GPU 上，通过 all-to-all 通信将 token 路由到对应 GPU 计算，再 all-to-all 收集结果**。
- **Dense 模型推理的特点**
- 计算图完全静态：每层的 FFN 权重固定，所有 token 走同一路径
- GEMM 形状规则：$[B \times S, H] \times [H, 4H]$，可以充分利用 Tensor Core
- 并行策略简单：Tensor Parallelism（按列/行切分权重）即可
- 显存占用 = 参数量 × bytes_per_param（可预测）
- 优化手段成熟：量化、CUDA Graph、算子融合都直接适用
- **MoE 模型推理的特殊挑战**
- **动态路由**：Router 输出决定每个 token 去哪个 Expert → 计算图数据依赖
- **稀疏激活**：如 Mixtral 8×7B，每 token 只激活 2/8 个 Expert → 有效计算量只有 Dense 的 25%
- **负载不均衡**：某些 Expert 被频繁选中 → 对应 GPU 成为瓶颈
- **显存占用大**：所有 Expert 权重都要存储（Mixtral 8×7B 总参数 46.7B，但每 token 只用 12.9B）
- **Kernel 形状不规则**：每个 Expert 收到的 token 数不同 → GEMM 的 M 维度动态变化
- **Expert Parallelism（EP）的实现**

```text
1. 每个 GPU 上所有 token 过 Router → 得到 top-k Expert 分配
2. All-to-All 通信：将 token 发送到持有对应 Expert 的 GPU
3. 每个 GPU 对收到的 token 执行本地 Expert 的 FFN 计算
4. All-to-All 通信：将计算结果送回原始 GPU
5. 加权求和（top-k 权重 × Expert 输出）
```

- **权重分布**：将 N 个 Expert 均匀分配到 P 个 GPU 上，每个 GPU 存 N/P 个 Expert
- **前向流程**：
- **通信模式**：两次 all-to-all（dispatch + combine），通信量 = $2 \times B \times S \times H \times \text{bytes}$
- **负载均衡**：Capacity Factor（每个 Expert 最多处理的 token 数），超出则 drop 或 overflow
- **工程实现细节**
- **vLLM 的 MoE 实现**：用 `fused_moe` kernel，将 Router + Permute + GEMM + Unpermute 融合
- **Megablocks**：将不规则的 Expert GEMM 转化为 block-sparse GEMM，避免 padding 浪费
- **DeepSpeed-MoE**：支持 EP + TP + DP 的 3D 并行
- **动态 batch 处理**：不同 Expert 收到的 token 数不同 → 用 grouped GEMM 或 padded batch
- 面试关键句：**"MoE 推理的核心矛盾是：计算是稀疏的（好事），但通信和调度是密集的（坏事）"**

#### 1. MoE 架构中，专家路由是针对每个 token 进行还是针对每个序列进行？

- 答案是**针对每个 token 进行路由**，这是 MoE 架构最核心的设计决策之一。具体来说，在 Transformer 的每一层 MoE FFN 中，每个 token 的隐藏状态 $x_t$ 会独立地经过门控网络（Router/Gate）计算出一组路由分数，然后选择 Top-K 个专家进行计算。这意味着**同一个序列中不同的 token 可能被分配到完全不同的专家**。比如一句话里，"Python"这个 token 可能激活代码相关的专家，而"beautiful"可能激活语言审美相关的专家。这种 token 级粒度的路由是 MoE 区别于传统集成学习（样本级路由）的关键所在。当然，也有研究探索过更粗粒度的路由（如 segment-level），ICLR 2026 有工作专门研究了"局部路由一致性"（Local Routing Consistency），发现某些 MoE 模型的路由模式在局部 segment 内确实比较稳定，这为专家卸载等优化提供了理论依据。但**主流生产模型（DeepSeek-V3、Llama 4、Qwen3-MoE）全部采用 token 级路由**。
- **Token 级路由的具体计算流程**
- 每个 token 的隐藏状态 $x_t \in \mathbb{R}^d$ 经过门控网络 $g(x_t) = W_g \cdot x_t$，得到 $E$ 个专家的路由分数（$E$ 为专家总数）
- 对分数做 softmax 归一化后，选取 **Top-K** 个专家（如 DeepSeek-V3 是 256 个路由专家中选 8 个）
- 输出为被选中专家的加权求和：$y_t = \sum_{i \in \text{TopK}} \text{softmax}(g(x_t))_i \cdot \text{Expert}_i(x_t)$
- 关键点：**路由决策是逐 token 独立的**，不同 token 之间没有显式的路由依赖（除非通过 attention 间接影响）
- 伪代码：

```python
gate_scores = gate(x_t)           # shape: (E,)
topk_scores, topk_indices = topk(softmax(gate_scores), k=K)
output = sum(topk_scores[i] * experts[topk_indices[i]](x_t) for i in range(K))
```

- **Token Choice vs Expert Choice：两种路由范式**
- **Token Choice（TC）**：每个 token 主动选择自己要去的专家，这是主流方案（Switch Transformer、DeepSeek-V3、Mixtral）
- **Expert Choice（EC）**：反过来，每个专家从所有 token 中选择自己要处理的 token（Zhou et al., 2022），天然保证负载均衡
- EC 的问题是：某些 token 可能不被任何专家选中（被丢弃），或者被过多专家选中，**破坏了计算的确定性**
- 2026 年的趋势：DeepSeek-V3 用**无辅助损失的偏置更新**替代传统 load balancing loss，在 Token Choice 框架下实现了接近 EC 的均衡效果
- **为什么不是序列级路由？**
- 序列级路由意味着整个句子/段落共享同一组专家，**丧失了 token 级的细粒度专业化能力**
- 一个序列中往往包含多种语义成分（实体、关系、逻辑连接词），需要不同专家处理
- 实验表明，token 级路由相比序列级路由在 perplexity 上有 **1-3 个点的优势**
- 但 token 级路由也带来了工程挑战：同一 batch 内不同 token 去不同专家，导致**不规则的通信模式**（all-to-all dispatch）
- **前沿探索：更粗粒度的路由是否可行？**
- ICLR 2026 论文提出 **SRP（Segment Routing Best Performance）** 指标，量化"段级路由"能多大程度模拟 token 级路由
- 发现：对于**局部路由一致性高**的模型（如某些训练充分的模型），segment 级路由能保留 90%+ 的性能
- 这为**专家卸载（Expert Offloading）** 提供了依据：如果路由模式在局部稳定，就可以预加载一组专家而非按需切换
- 另有 **Routing-Free MoE**（2026.4）尝试完全消除中心化路由，用分布式哈希或学习式分配替代，但仍处于研究阶段

#### 2. MoE 架构在模型参数量不断增长的背景下，为何仍能维持相对较高的训练效率？

- 核心答案一句话：**MoE 通过条件计算（Conditional Computation）实现了"参数量"和"计算量"的解耦**。总参数量可以非常大（如 DeepSeek-V3 的 671B），但每个 token 实际参与前向和反向计算的只有被激活的那部分参数（37B，约 5.5%）。这意味着 FLOPs 只与激活参数量成正比，而不是总参数量。从 Scaling Law 的角度看，MoE 让你用**接近小模型的训练成本，获得接近大模型的性能**。具体来说，如果你有一个 8 专家 Top-2 的 MoE 层，每个专家的大小和原来的 FFN 一样，那总参数是原来的 8 倍，但每个 token 的计算量只增加了 2 倍（激活 2 个专家）。这个"参数效率比"是 MoE 最核心的价值主张。当然，训练效率的维持还依赖于**专家并行（Expert Parallelism）** 等分布式策略，把不同专家放在不同 GPU 上，避免单卡显存瓶颈。
- **条件计算：参数与 FLOPs 的解耦**
- 稠密模型：每个 token 经过所有参数，FLOPs $\propto$ 总参数量 $N$
- MoE 模型：每个 token 只经过 Top-K 个专家，FLOPs $\propto$ 激活参数量 $N_{\text{active}} = N \times K/E$
- 以 DeepSeek-V3 为例：总参数 671B，激活参数 37B，**计算量仅为同规模稠密模型的约 5.5%**
- 以 Kimi K2 为例：总参数 1.04T，激活参数 32B，激活比约 3%
- 关键洞察：**模型容量（memory/knowledge）由总参数决定，计算成本由激活参数决定**
- **Scaling Law 视角下的 MoE 优势**
- Chinchilla Scaling Law 表明：最优训练需要 $C \approx 6ND$（$N$ 为参数量，$D$ 为数据量）
- 对于稠密模型，增大 $N$ 意味着训练成本线性增长
- MoE 的"等效"：用 $N_{\text{active}}$ 的 FLOPs 获得接近 $N_{\text{total}}$ 的性能，**打破了 FLOPs-Performance 的线性约束**
- 实验数据：Mixtral 8x7B（46.7B 总参，12.9B 激活）性能接近 Llama 2 70B，但 FLOPs 只有后者的约 1/5
- 这意味着 MoE 在 **compute-optimal frontier** 上占据了更优的位置
- **专家并行（Expert Parallelism）的分布式训练策略**
- 核心思想：将不同专家分配到不同 GPU 上，每个 GPU 只存储和计算部分专家
- 前向传播时通过 **All-to-All 通信**将 token dispatch 到对应专家所在的 GPU
- 与 Tensor Parallelism（TP）和 Pipeline Parallelism（PP）正交，可以组合使用
- 典型配置（DeepSeek-V3）：EP（Expert Parallelism）+ DP（Data Parallelism）+ PP
- 华为的优化方案（Adaptive Pipe & EDPB）通过**计算-通信 overlap** 将 MoE 训练效率提升 70%
- **与稠密模型的训练效率对比**

| 维度 | 稠密模型（如 Llama 3 70B） | MoE 模型（如 DeepSeek-V3 671B） |
| --- | --- | --- |
| 总参数量 | 70B | 671B |
| 每 token 激活参数 | 70B（100%） | 37B（5.5%） |
| 每 token FLOPs | ~140 GFLOPs | ~74 GFLOPs |
| 显存需求（参数） | ~140GB (FP16) | ~1.3TB (FP16) |
| 训练吞吐量 | 基准 | 接近基准（因 FLOPs 相当） |
| 性能（benchmark） | 基准 | 显著优于基准 |

- **训练效率的隐性成本**
- 虽然 FLOPs 降低了，但 **All-to-All 通信开销**是 MoE 训练独有的额外成本
- 当专家数多、batch 内 token 分布不均时，通信可能成为瓶颈（**一半以上训练时间可能在等待通信**）
- 解决方案：容量因子（capacity factor）限制每个专家接收的 token 数上限，超出则丢弃
- DeepSeek-V3 的**无 token 丢弃策略**：通过动态偏置调整路由，避免丢弃，但增加了路由计算的复杂度

#### 3. MoE 架构为何能在参数量极大的情况下控制训练和推理成本，其真正的技术难点在哪里？

- MoE 控制成本的原理很清晰：**稀疏激活让计算量只与激活参数成正比，而非总参数**。一个 671B 的 MoE 模型，每个 token 只做 37B 参数的前向计算，推理时的 FLOPs 和一个 37B 的稠密模型差不多。但真正的技术难点不在"算得快"，而在**三个层面的工程挑战**：第一是**负载均衡**——如果大量 token 涌向少数专家，MoE 就退化为稠密模型(Dense)，热门专家成为瓶颈；第二是**通信开销**——专家分布在不同 GPU 上，token 的 dispatch 和 combine 需要 All-to-All 通信，这在大规模集群中代价极高；第三是**显存墙**——虽然计算是稀疏的，但**所有专家的参数都必须常驻显存**（或至少可快速访问），671B 参数即使用 FP8 也需要约 671GB 显存。这三个问题互相耦合，构成了 MoE 从"理论上高效"到"工程上可用"的核心鸿沟。
- **成本控制的核心机制：稀疏激活**
- 前向传播：每个 token 只经过 Top-K 个专家，FLOPs = $O(K/E \times N_{\text{total}})$
- 反向传播：梯度也只回传到被激活的专家，**未激活专家的参数不更新**
- 推理时：KV Cache 与 Attention 层相关（不受 MoE 影响），FFN 层的计算量由激活参数决定
- 实际效果：DeepSeek-V3 的推理成本约为同性能稠密模型的 **1/4 到 1/5**
- 但注意：**显存占用并不稀疏**——所有专家参数必须加载，这是 MoE 的"隐性成本"
- **技术难点一：负载均衡（Load Balancing）**
- 问题本质：训练初期路由网络未充分学习，容易出现**赢者通吃（winner-take-all）** 现象
- 后果：少数专家被过度使用（hot experts），其他专家"饿死"（cold experts），**模型退化为小稠密模型**
- 传统方案：在 loss 中加入辅助负载均衡损失 $\mathcal{L}_{\text{aux}} = \alpha \cdot N \cdot \sum_i f_i \cdot P_i$（$f_i$ 为专家 $i$ 被分配的 token 比例，$P_i$ 为路由概率均值）
- DeepSeek-V3 的创新：**无辅助损失的动态偏置更新**——在训练过程中动态调整每个专家的路由偏置 $b_i$，被过度选择的专家偏置减小，反之增大
- ICML 2026 新发现（RepetitionCurse）：重复 token 输入可以导致**路由坍塌（routing collapse）**，大量 token 集中到少数专家，这是 MoE 服务端的系统级安全风险
- **技术难点二：All-to-All 通信瓶颈**
- 在专家并行中，每个 GPU 上的 token 需要被 dispatch 到持有对应专家的 GPU，计算完再 combine 回来
- 这是一个**全局 All-to-All 通信**，通信量 = $O(B \times n \times d \times K)$（batch × 序列长度 × 隐藏维度 × Top-K）
- 当集群规模大（如 2048 GPU）时，All-to-All 的延迟和带宽需求成为**训练效率的主要瓶颈**
- 华为实测：未优化时，**超过 50% 的训练时间花在通信等待上**
- 优化方案：
  - **计算-通信 overlap**：在等待 All-to-All 的同时计算 Attention 层
  - **Selective R/S（Reduce-Scatter）**：减少冗余通信，节省 70% 通信内存
  - **EP + DP 混合并行**：在节点内用 EP，节点间用 DP，减少跨节点 All-to-All
- **技术难点三：显存墙与专家卸载**
- 矛盾点：计算是稀疏的（只用 K/E 的参数），但**存储是稠密的**（所有 E 个专家必须可访问）
- DeepSeek-V3 671B 参数，FP16 下需要 ~1.3TB 显存，即使 FP8 也需要 ~671GB
- 单卡（H100 80GB）远远不够，必须多卡分布 → 引入通信问题
- **专家卸载（Expert Offloading）**：将冷专家放在 CPU/SSD，热专家留在 GPU
- 但 ICLR 2026 研究表明：**不是所有 MoE 模型都适合卸载**——路由一致性低的模型，专家切换频繁，卸载反而增加延迟
- 前沿方案：EaaS（Expert-as-a-Service）将专家拆为独立微服务，按需调度，降低 37.5% 成本
- **技术难点四：训练稳定性与专家坍塌**
- **专家坍塌（Expert Collapse）**：训练过程中多个专家学到几乎相同的表示，等价于浪费了参数
- 原因：路由网络的梯度信号弱（Top-K 选择是不可微的），专家缺乏足够的差异化压力
- 解决方案：
  - **细粒度专家分割**（DeepSeekMoE）：将大专家拆成多个小专家，增加多样性
  - **共享专家隔离**：设置固定的共享专家处理通用知识，路由专家只负责专业化
  - **ReMoE（ICLR 2025）**：用 ReLU 替代 softmax+TopK，实现完全可微路由
  - **Z-loss**：对路由 logits 加正则化，防止数值过大导致路由退化
- 常见陷阱：load balancing loss 的系数 $\alpha$ 非常敏感，太大会损害模型性能，太小则无法有效均衡

### 三、专家负载均衡机制、路由分配规律

#### 1. MoE 模型中路由模块是怎样决定将 token 分配给哪些专家的？什么原因会导致专家之间的负载出现严重不均？

- 路由模块的决策过程其实就是一个**打分-排序-选择**的流程。每个 token 的隐藏状态 $x_t$ 经过一个线性层（门控网络）得到 $E$ 个专家的 logits，经过 softmax 归一化后取 Top-K 个专家，被选中的专家按归一化权重加权求和产出最终输出。以 DeepSeek-V3 为例，256 个路由专家中选 8 个，再加上 1 个始终激活的共享专家。导致负载不均的原因是多方面的：**训练初期的随机性**会让某些专家偶然获得更多 token，形成正反馈循环（马太效应）；**输入数据的分布偏斜**（比如代码数据远少于自然语言）会让处理高频领域的专家被过度使用；**路由网络的梯度信号弱**（Top-K 选择是不可微的），导致路由策略难以自我纠正。最极端的情况是**赢者通吃（winner-take-all）**：一两个专家垄断了几乎所有 token，其他专家完全"饿死"，MoE 退化为小 Dense 模型。
- **路由决策的完整计算流程**
- 门控网络：$g(x_t) = W_g \cdot x_t + b$，其中 $W_g \in \mathbb{R}^{E \times d}$，输出 $E$ 维 logits
- 归一化：$\hat{g}(x_t) = \text{softmax}(g(x_t))$，得到每个专家的概率分数
- Top-K 选择：$\mathcal{S} = \text{TopK}(\hat{g}(x_t), K)$，选出 K 个专家的索引
- 重归一化：对选中的 K 个分数再做一次 softmax（或简单归一化），得到最终权重 $w_i$
- 加权求和：$y_t = \sum_{i \in \mathcal{S}} w_i \cdot \text{Expert}_i(x_t)$
- DeepSeek-V3 的特殊设计：使用**有限制路由（constrained routing）**，确保每个专家在一个 batch 内接收的 token 数不超过容量上限 $C = \text{capacity\_factor} \times \frac{B \times n \times K}{E}$
- **负载不均的根因分析**
- **正反馈循环（Rich-Get-Richer）**：训练初期，某个专家偶然获得稍多的 token → 梯度更新更充分 → 路由分数更高 → 获得更多 token → 循环加剧
- **数据分布偏斜**：如果训练数据中 80% 是英文文本、10% 代码、10% 数学，那么处理通用语言的专家天然会被更频繁激活
- **Top-K 的不可微性**：$\text{argmax}$ 和 $\text{TopK}$ 操作没有梯度，路由网络只能通过被选中专家的 loss 间接获得信号，**纠正能力很弱**
- **专家初始化相似性**：如果所有专家初始化参数接近（如相同的随机种子），早期路由分数差异极小，微小的数值波动就会被放大
- **RL 场景的特殊性**：reward 信号可能引导模型"走捷径"，反复使用某几个已经能产出高 reward 的专家，加剧路由坍塌
- **负载不均的量化指标**
- **专家利用率**：$u_i = \frac{\text{专家 } i \text{ 实际处理的 token 数}}{\text{理想均匀分配下的 token 数}}$，理想值为 1.0
- **负载不均衡系数**：$\text{Imbalance} = \frac{\max_i(u_i)}{\min_i(u_i)}$，越大越不均衡
- **路由熵**：$H = -\sum_i p(e_i) \log p(e_i)$，最大值为 $\log E$（完全均匀），越小越集中
- **死亡专家比例**：利用率低于阈值（如 0.1）的专家占比，DeepSeek-V3 要求这个比例接近 0
- 监控工具：训练过程中实时记录每个专家每层的 token 接收量，画成热力图或折线图
- **主流模型的应对策略对比**

| 模型 | 路由策略 | 负载均衡方法 | 特殊设计 |
| --- | --- | --- | --- |
| Switch Transformer | Top-1 | 辅助 loss + capacity factor | 容量因子限制丢弃溢出 token |
| DeepSeek-V3 | Top-8/256 | **无辅助 loss 的动态偏置** | 共享专家 + 细粒度专家分割 |
| Mixtral 8x7B | Top-2/8 | 辅助 loss | 无共享专家 |
| Llama 4 | Top-K/128 | 辅助 loss + 路由温度 | 早期层用 Dense，后期层用 MoE |
| Kimi K2 | Top-K/384 | 辅助 loss | 1.04T 总参，32B 激活 |

#### 2. MoE 中的负载均衡通常采用哪些方法，为何部分模型 loss 表现正常但 expert 已经退化？

- 负载均衡方法从大的维度可以分为三类：**训练时的损失约束**（辅助 loss、Z-loss）、**路由策略设计**（动态偏置、Expert Choice、Noisy Top-K）、**系统级调度**（EPLB、LPLB、容量因子）。但这个问题最有价值的部分其实是后半句——**为什么 loss 正常但专家已经退化？** 这是一个非常隐蔽的陷阱。核心原因是：MoE 的总 loss 是所有专家加权输出的结果，**即使多个专家学到了几乎相同的东西，加权求和的输出仍然可以是正确的**。打个比方，8 个专家如果都学到了"正确答案的 1/8"，加起来还是正确答案，loss 完全正常。但实际上模型只用了 1 个专家的容量，其他 7 个是冗余的。这就是 ICLR 2026 阿里工作揭示的**专家同质化**问题——loss 曲线看起来很漂亮，但模型的**有效参数量远小于名义参数量**，Scaling 能力被严重封顶。
- **主流负载均衡方法全景**
- **辅助负载均衡损失**：$\mathcal{L}_{\text{aux}} = \alpha \cdot N \cdot \sum_i f_i \cdot P_i$，最经典但最"粗暴"
- **Router Z-Loss**：$\mathcal{L}_z = \frac{1}{B} \sum_t \log^2(\sum_i e^{g(x_t)_i})$，惩罚路由 logits 的绝对值过大，防止路由过度自信
- **动态偏置（DeepSeek-V3）**：无辅助 loss，通过实时调整偏置 $b_i$ 实现均衡
- **Expert Choice 路由**：反转选择方向，天然均衡但有 token 丢弃风险
- **系统级方案**：EPLB（冗余专家复制）、LPLB（线性规划全局优化）、容量因子限制
- 实际生产中通常是**多种方法组合使用**，比如 DeepSeek-V3 = 动态偏置 + 共享专家 + 细粒度分割 + EPLB
- **Loss 正常但专家退化的根因**
- **加权求和的"掩盖效应"**：$y = \sum_i w_i \cdot E_i(x)$，即使 $E_1 \approx E_2 \approx \cdots \approx E_N$，只要 $\sum w_i = 1$，输出仍然正确
- **梯度信号的"搭便车"问题**：所有专家收到相同的梯度方向（因为 loss 对每个专家的梯度都通过 $w_i$ 加权），**缺乏差异化的学习压力**
- **Load balancing loss 的"虚假均衡"**：它只约束 $f_i$（边际分布）接近均匀，不约束 $p(e_i | \text{domain})$（条件分布），专家可以在"被均匀使用"的同时"做相同的事"
- **路由网络的低秩性**：如果 $W_g$ 的有效秩很低，所有 token 的路由分数差异很小，Top-K 选择接近随机，专家分工无从谈起
- **如何检测"隐性退化"**
- **专家输出相似度矩阵**：计算 $E \times E$ 的余弦相似度矩阵，如果均值 > 0.85，高度怀疑同质化
- **有效秩分析**：将所有专家的输出向量堆叠成矩阵，计算其**有效秩**（如通过奇异值衰减速度），有效秩远低于专家数说明退化
- **条件路由互信息**：$I(\text{expert}; \text{domain})$ 接近 0 说明专家选择与输入领域无关
- **消融选择性**：去掉任一专家后性能下降幅度是否一致——一致说明冗余，不一致说明有分工
- **路由熵的时间曲线**：如果训练过程中路由熵持续下降并趋近于 $\log K$（只关注 Top-K 个），说明路由在固化
- **解决方案与最佳实践**
- **Expert Divergence Learning（ICLR 2026）**：引入域间多样性损失，将路由多样性引导到"不同领域激活不同专家"
- **专家输出正交正则化（NeurIPS 2025）**：$\mathcal{L}_{\text{orth}} = \sum_{i \neq j} \|Y_i^T Y_j\|_F^2$，强制不同专家的输出在表征空间中正交
- **共享专家隔离**：设置 1-2 个始终激活的共享专家处理通用知识，路由专家只负责差异化，**减少"所有专家都学通用知识"的动机**
- **监控 checklist**：训练过程中同时监控 loss、路由熵、专家利用率标准差、专家输出相似度，**任何一项异常都需要干预**
- 常见陷阱：不要只看 loss 曲线就认为训练正常，**MoE 的 loss 是最不可靠的健康指标**

#### 3. 当部分专家的利用率明显偏低时，可以通过哪些手段改进路由策略来提高利用率？

- 专家利用率低是 MoE 训练中最常见的问题之一，解决思路可以从**路由策略本身、损失函数设计、架构调整、工程手段**四个层面入手。最经典的方法是加入**辅助负载均衡损失**，惩罚路由分布偏离均匀分布。但这个方法有个已知缺陷——它只保证"所有专家都被用到"，不保证"被有意义地用到"，可能导致专家同质化。DeepSeek-V3 提出了更优雅的方案：**无辅助损失的动态偏置更新**，在训练过程中实时调整每个专家的路由偏置，被过度选择的专家偏置自动减小，冷门专家偏置增大。更激进的方法包括 **Expert Choice 路由**（让专家选 token 而非 token 选专家，天然均衡）、**ReLU 路由**（ReMoE，完全可微，消除 Top-K 的梯度断裂）、以及**专家重置/再初始化**（将死亡专家的参数重新初始化为活跃专家的扰动版本）。
- **辅助负载均衡损失（Auxiliary Load Balancing Loss）**
- 经典公式（Switch Transformer）：$\mathcal{L}_{\text{aux}} = \alpha \cdot N \cdot \sum_{i=1}^{N} f_i \cdot P_i$
- $f_i$：专家 $i$ 被分配的 token 比例（离散统计量），$P_i$：专家 $i$ 的路由概率均值（连续可微量）
- 当所有专家负载均匀时，$f_i = P_i = 1/N$，loss 取最小值
- **系数 **$\alpha$** 非常敏感**：太大（如 0.1）会严重损害模型性能，太小（如 0.001）则均衡效果不明显，通常取 0.01~0.01
- 陷阱：这个 loss 鼓励的是**边际均匀**，不关心条件分布，可能导致所有专家学到相同的"平均"表示
- **DeepSeek-V3 的无辅助损失动态偏置**
- 核心思想：不修改 loss，而是**直接修改路由 logits**
- 每个专家维护一个可调整的偏置 $b_i$，路由分数变为 $g(x_t)_i + b_i$
- 训练过程中，如果专家 $i$ 被过度选择（超过目标比例），$b_i$ 自动减小；反之增大
- 更新规则类似 PID 控制器：$b_i \leftarrow b_i - \eta_b \cdot (f_i - 1/N)$
- 优势：**不引入额外的 loss 项，不干扰主任务的梯度信号**，且能实时适应数据分布的变化
- 实验表明，这种方法在保持模型性能的同时，将专家利用率的标准差降低了约 60%
- **路由策略的架构级改进**
- **Expert Choice（EC）路由**：反转选择方向，每个专家从所有 token 中选自己要处理的，天然保证每个专家处理相同数量的 token
- **ReMoE（ICLR 2025）**：用 ReLU 替代 softmax + TopK，$w_i = \text{ReLU}(g(x_t)_i)$，ReLU 天然将负值置零实现稀疏化，且**完全可微**
- **路由温度调节**：在 softmax 前除以温度 $\tau$，$\text{softmax}(g(x_t) / \tau)$，高温使分布更均匀，低温使分布更尖锐
- **Noisy Top-K**：在路由 logits 上加高斯噪声 $g(x_t) + \epsilon$，增加探索性，防止路由过早固化
- **多粒度路由**：DeepSeekMoE 的细粒度专家分割——将一个大专家拆成多个小专家，增加路由的"分辨率"
- **工程级干预手段**
- **专家重置（Expert Reset）**：当检测到某专家连续 $T$ 步利用率低于阈值，将其参数重新初始化为当前最活跃专家参数的随机扰动
- **容量因子（Capacity Factor）**：设置每个专家接收 token 的上限 $C = c_f \times \frac{B \cdot n \cdot K}{E}$，超出部分被丢弃或溢出到备用专家
- **Expert Parallelism 层面的重分配**：DeepSeek 的 EPLB/LPLB 在系统层面将热门专家复制到多个 GPU，冷门专家合并，**从硬件调度角度缓解不均**
- **数据层面的领域均衡采样**：在训练数据采样时，对不同领域做上采样/下采样，从源头减少分布偏斜
- 常见陷阱：容量因子设太小会导致大量 token 被丢弃（信息损失），设太大则均衡效果不明显

### 五、异构推理加速与 MoE 大规模工程部署优化（DeepSeek EPLB 等）

#### 1. 介绍 DeepSeek V3 中 EPLB 的推理机制(系统级调度)

- EPLB 全称 **Expert Parallelism Load Balancer**，是 DeepSeek 在 2025 年 2 月开源周第四天发布的工具，专门解决 MoE 模型在专家并行（EP）部署时的**GPU 负载不均问题**。核心思想非常直觉：既然不同专家被激活的频率差异很大，那就**把热门专家复制到多个 GPU 上，冷门专家合并到少数 GPU 上**，让每个 GPU 的总计算量尽量接近。EPLB 提供了两种策略：**层次化负载均衡（Hierarchical LB）** 适用于节点内 NVLink 互联的场景，**全局负载均衡（Global LB）** 适用于跨节点的场景。在推理时，EPLB 根据离线 profiling 得到的专家负载统计，预先计算好专家到 GPU 的映射方案，运行时 token 被 dispatch 到持有对应专家（或其副本）的 GPU 上计算。2025 年 11 月 DeepSeek 又进一步开源了 **LPLB（Linear-Programming-Based Load Balancer）**，用线性规划求解器替代启发式算法，实现了更精确的全局最优分配。
- **EPLB 的核心机制：冗余专家策略**
- **问题背景**：在 EP 中，$E$ 个专家均匀分配到 $G$ 个 GPU 上，每个 GPU 持有 $E/G$ 个专家。但热门专家接收的 token 可能是冷门专家的 10 倍以上
- **冗余专家（Redundant Experts）**：将负载最高的专家**复制**到多个 GPU 上，每个副本称为一个冗余专家
- 每个冗余专家**链接到一个原始专家**，形成 GPU 之间的连接边（edge）
- **边容量（Edge Capacity）**：定义为当前 batch 中分配给该冗余专家的 token 数量，决定了最大 token 流量
- 运行时，token 可以被路由到原始专家或其任一副本，**分散热门专家的计算压力**
- **两种负载均衡策略**
- **层次化负载均衡（Hierarchical LB）**：
  - 适用于节点内（NVLink 互联，带宽高、延迟低）
  - 先在节点内做局部均衡，再在节点间做全局调整
  - 优势：通信量小，因为大部分 token 在节点内就能找到专家副本
- **全局负载均衡（Global LB）**：
  - 将所有 GPU 视为一个平面，全局搜索最优的专家-GPU 映射
  - 使用启发式算法（贪心 + 局部搜索）最小化 $\max_g(\text{load}_g)$
  - 适用于跨节点场景，但通信开销更大
- 实际部署中通常**两者结合**：节点内用 Hierarchical，节点间用 Global
- **LPLB：线性规划的进阶方案（2025.11）**
- 将 token 分发问题建模为**带约束的线性规划（LP）问题**
- 目标函数：$\min \max_g(\text{load}_g)$（最小化最大 GPU 负载）
- 约束条件：每个 token 必须被分配给其 Top-K 专家之一；每个 GPU 的容量不超过硬件上限
- 使用 **GPU 优化的内点法（Interior Point Method）** 求解，延迟在毫秒级
- 相比 EPLB 的启发式方法，LPLB 能找到**全局最优解**，负载不均衡度降低约 30%
- 与 NVIDIA 在万卡集群中用类似机制分配 SM（Streaming Multiprocessors）的思路一致
- **推理时的完整工作流**
- **离线阶段**：在代表性数据上运行 profiling，统计每个专家在每个 batch 中的 token 接收量
- **规划阶段**：EPLB/LPLB 根据负载统计，计算专家到 GPU 的最优映射（包括哪些专家需要复制、复制到哪些 GPU）
- **运行时**：
  - Token 经过路由网络得到 Top-K 专家索引
  - 根据预计算的映射，将 token dispatch 到持有对应专家的 GPU
  - 各 GPU 并行计算专家前向
  - 结果 combine 回原始 GPU
- 关键优化：dispatch 和 combine 的 All-to-All 通信与 Attention 层的计算**做 overlap**（DualPipe 策略）

#### 2. 在 MoE 模型的推理优化方面是否有实践经验？专家调度+通信+批处理

- MoE 推理优化的核心矛盾在于：**计算是稀疏的但存储是稠密的**。一个 671B 的 MoE 模型，每个 token 只激活 37B 参数，但所有 671B 参数都必须可访问。从实践角度，MoE 推理优化主要围绕四个方向：**KV Cache 管理**（PagedAttention、前缀缓存）、**专家调度**（EPLB、专家预加载/卸载）、**通信优化**（DeepEP 的 fused dispatch/combine kernel）、**批处理策略**（continuous batching、动态 padding）。MLSys 2026 的 MoE 推理优化挑战赛上，清华和腾讯混元团队通过全链路优化将推理速度提升了 4.1 倍，说明这个方向仍有巨大的优化空间。
- **Prefill 与 Decode 阶段的差异化优化**
- **Prefill 阶段**（处理 prompt）：
  - 整个序列一次性计算，Attention 是 compute-bound，适合 FlashAttention
  - MoE FFN 中，大量 token 同时路由，可以做**批量 GEMM**（将同一专家的所有 token 合并为一次矩阵乘法）
  - 优化重点：减少 All-to-All 通信延迟，使用 DeepEP 的 fused kernel
- **Decode 阶段**（逐 token 生成）：
  - 每步只有 1 个新 token，Attention 退化为向量-矩阵乘，**memory-bound**
  - MoE FFN 中，只有 K 个专家被激活，每个专家只处理 1 个 token，**GPU 利用率极低**
  - 优化重点：减少 KV Cache 读取带宽、专家权重的预加载和缓存
- RL 场景中 rollout 主要是 decode，training 主要是 prefill，**需要针对两阶段分别优化**
- **专家调度与显存管理**
- **专家预加载**：根据路由统计，预测下一步可能激活的专家，提前从 HBM 加载到 SRAM/L2 Cache
- **专家卸载（Expert Offloading）**：将冷门专家放在 CPU 内存或 NVMe SSD 上，按需加载
  - ICLR 2026 的研究表明：**路由一致性高的模型适合卸载**（专家切换少），路由一致性低的模型不适合
- **EaaS（Expert-as-a-Service）**：将专家拆为独立微服务，通过 RPC 按需调用，降低 37.5% 显存成本
- **FP8/INT8 量化**：专家权重用低精度存储，推理时按需反量化，显存占用减半
- **MLA 与 MoE 的协同**：DeepSeek-V3 的 MLA 压缩 KV Cache，MoE 压缩 FFN 计算，两者结合使推理显存降低约 60%
- **通信优化：DeepEP 与 Fused Kernel**
- **DeepEP**：DeepSeek 开源的专家并行通信库，提供高度优化的 dispatch/combine kernel
- 核心优化：将 All-to-All 通信与专家计算**fuse 到一个 CUDA kernel** 中，减少 kernel launch 开销
- 支持 **NVLink（节点内）和 RDMA（节点间）** 的混合通信
- 在 RL 场景中，rollout 和 training 的通信模式不同：rollout 是"一对多"（一个 token 去 K 个专家），training 是"多对多"（batch 内所有 token 重新分配）
- **计算-通信 overlap**：在等待 All-to-All 的同时计算 Attention 层，DualPipe 实现了完全 overlap
- **RL 场景的特殊优化**
- **Rollout 吞吐优化**：使用 vLLM/SGLang 的 continuous batching，不同长度的生成请求动态组 batch
- **前缀缓存（Prefix Caching）**：RL 中同一 prompt 可能生成多个回答（如 GRPO 的 group），共享 prompt 的 KV Cache
- **投机解码（Speculative Decoding）**：用小模型（或 MoE 的共享专家）做 draft，大模型做 verify，加速 decode
- **异步 pipeline**：rollout 和 training 在不同 GPU 组上并行执行，通过消息队列传递数据
- 实践经验：RL 场景中 **rollout 时间通常占 60-70%**，优化 rollout 吞吐比优化 training 效率更有价值

### 八、纯训练

#### 4. 通过什么方式可以判断一个 MoE 模型真正实现了专家间的分工协作，而不是简单地把 Dense 模型做了参数切分？

- 这个问题问得非常好，也是 MoE 研究中一个核心但容易被忽视的问题。简短回答：**仅凭 loss 下降和 benchmark 分数是无法判断的**，必须从多个维度做"专家行为分析"。最直接的判断方式是看**路由分布的多样性**和**专家输出的差异性**。如果所有专家对同一类输入给出几乎相同的输出，那即使路由看起来是分散的，本质上也只是把 Dense FFN 切成了几块做"伪并行"。ICLR 2026 阿里的工作明确揭示了这个问题——他们发现 15B 参数的 MoE 模型中 8 个专家学到了几乎相同的东西，称之为**专家同质化（Expert Homogenization）**。判断真正分工的方法包括：分析路由矩阵的**条件熵**（不同输入是否激活不同专家）、计算专家输出之间的**余弦相似度**（是否足够低）、做**专家消融实验**（去掉某个专家后特定领域性能是否显著下降）、以及观察**路由模式的领域相关性**（代码 token 是否稳定路由到某些专家，自然语言 token 是否路由到另一些）。真正实现了分工的 MoE，应该表现出"**路由有结构、输出有差异、消融有选择性**"这三个特征。
- **路由分布分析：条件熵与路由模式**
- 计算每个专家被选中的**边际概率** $p(e_i)$：如果所有专家被选中的概率接近 $1/E$，说明路由是均匀的，但均匀≠有分工
- 更关键的是**条件路由分布** $p(e_i | \text{domain})$：按输入类型（代码/数学/自然语言/多语言）分组，看不同领域的路由模式是否有显著差异
- 用**互信息** $I(\text{expert}; \text{domain})$ 量化专家选择与输入领域之间的相关性，互信息越高说明分工越明确
- 可视化路由矩阵的热力图：真正有分工的模型，热力图应该呈现**块状结构**（某些专家在某些领域被高频激活），而不是均匀的噪声
- 工具：可以用 `matplotlib` 画 $E \times D$ 的热力图（$E$ 为专家数，$D$ 为领域数），或者用 t-SNE 对路由向量做降维可视化
- **专家输出差异性：表征空间分析**
- 对同一批输入，分别收集每个专家的输出 $y_i = \text{Expert}_i(x)$，计算**两两余弦相似度矩阵**
- 如果所有专家输出的余弦相似度 > 0.9，说明专家高度同质化，**本质上等价于一个更宽的 Dense FFN**
- NeurIPS 2025 的工作（Advancing Expert Specialization for Better MoE）提出用**专家输出正交性**作为正则化目标，强制不同专家的输出在表征空间中正交
- 另一个指标：**专家输出的方差比**——如果专家间方差远小于专家内方差，说明专家没有学到差异化的特征
- 代码示例：

```python
# 收集所有专家对同一batch的输出
expert_outputs = [expert(x) for expert in experts]  # list of (B, d)
# 计算两两余弦相似度
sim_matrix = torch.stack([F.cosine_similarity(o1.unsqueeze(0), o2.unsqueeze(0), dim=-1)
                           for o1 in expert_outputs for o2 in expert_outputs])
# 如果 sim_matrix 均值 > 0.9，专家同质化严重
```

- **消融实验：选择性性能下降**
- 真正的分工应该表现为：**去掉专家 A 后，代码任务性能显著下降但数学任务不受影响**
- 如果去掉任何一个专家，所有任务的性能下降幅度都差不多，说明专家之间是**冗余的**，没有真正的专业化
- 具体做法：将某个专家的输出替换为所有专家输出的均值（模拟"去专业化"），观察不同领域 benchmark 的变化
- DeepSeek-V3 的**共享专家 + 路由专家**设计本身就是为了确保分工：共享专家处理通用知识，路由专家负责领域专业化
- 注意：消融实验的成本较高（需要多次推理），可以用**路由权重归零**作为轻量替代
- **前沿方法：Expert Divergence Learning（ICLR 2026）**
- 阿里团队发现，传统的 **load balancing loss 只保证"所有专家都被用到"，但不保证"被不同领域用到"**
- 他们提出将总路由多样性分解为**域间多样性（Inter-Domain Divergence）** 和**域内多样性（Intra-Domain Divergence）**
- 核心损失函数：$\mathcal{L}_{\text{EDL}} = -\text{InterDiv} + \lambda \cdot \text{IntraDiv}$，鼓励不同领域激活不同专家，同一领域内路由可以灵活
- 利用预训练数据中天然存在的**领域标签**（代码/数学/文本等）作为监督信号，引导专家分化
- 实验结果：在 15B MoE 模型上，EDL 使专家间输出余弦相似度从 0.92 降到 0.45，**下游任务平均提升 2.3 个点**

#### 3. 针对 MoE 模型和多模态模型的训练过程，目前还有哪些可以优化的方向？

- 这个问题比较开放，我从**架构设计、训练策略、系统工程、评估方法**四个维度来谈。架构层面，**路由机制的可微化**（如 ReMoE）和**专家分化的显式引导**（如 EDL）是两个明确的方向；训练策略层面，**RL 与 MoE 的协同优化**（R3、mechanism-aware reward）刚刚起步，还有大量空间；系统工程层面，**异构硬件适配**（GPU + NPU 混合部署）和**动态专家调度**（根据输入实时调整专家-GPU 映射）是落地的关键瓶颈；评估层面，目前缺乏**统一的 MoE 健康度评估框架**，很多退化问题在上线后才被发现。多模态 MoE 还有额外的挑战：不同模态（文本/图像/音频）的 token 数量和分布差异极大，路由策略需要**模态感知**。
- **架构设计方向**
- **可微路由**：ReMoE（ReLU 路由）消除了 Top-K 的梯度断裂，但稀疏度不可控；未来方向是**可学习稀疏度**的路由
- **层次化 MoE**：不同层使用不同数量的专家（浅层少、深层多），或不同层使用不同的 Top-K
- **模态感知路由**：多模态 MoE 中，为不同模态设计独立的路由网络或路由偏置
  - CVPR 2026 的 MoDES 工作发现，多模态 MoE 中 **88% 的专家计算是冗余的**，可以安全跳过
- **动态专家数量**：根据输入复杂度动态决定激活多少个专家（简单输入用 2 个，复杂输入用 8 个）
- **专家共享与继承**：在 continual learning 场景中，新任务复用旧专家 + 新增少量专家，避免灾难性遗忘
- **训练策略方向**
- **RL + MoE 的深度协同**：
  - 路由重放（R3）解决了训练-推理一致性，但**牺牲了路由探索**
  - 未来方向：在 R3 基础上加入**受控探索**（如 $\epsilon$-greedy 路由），平衡一致性和多样性
- **课程学习（Curriculum Learning）与 MoE**：先用简单数据训练路由网络，再逐步引入复杂数据，避免早期路由固化
- **多任务 MoE 训练**：不同任务共享部分专家、独占部分专家，类似 PLE（Progressive Layered Extraction）的思路
- **专家蒸馏**：训练完成后，将多个相似专家的知识蒸馏到一个专家中，**压缩模型而不损失性能**
- **系统工程方向**
- **异构硬件适配**：
  - 蚂蚁集团已验证在国产芯片上训练 MoE 模型，效果与 H800 相当，成本降低 20%
  - 挑战：不同芯片的通信原语不同，All-to-All 的实现需要深度适配
- **动态专家调度**：
  - 当前 EPLB/LPLB 是**静态规划**（离线 profiling → 固定映射），未来方向是**在线动态调整**
  - 根据实时负载统计，每隔 N 步重新计算专家-GPU 映射
- **MoE 推理的编译优化**：
  - MLSys 2026 冠军方案：E-Shard 策略（专家权重分片）、PSUM 批量读出、专门 GEMV 路径
  - 将 MoE 的 dispatch-compute-combine 编译为一个融合的 CUDA kernel
- **显存-计算 trade-off**：在显存充足时用更多专家副本减少通信，在显存紧张时用更少副本增加通信
- **评估与监控方向**
- **MoE 健康度 Dashboard**：集成路由熵、专家利用率、输出相似度、有效秩等指标，实时可视化
- **自动化退化检测**：设置阈值告警，当检测到路由坍塌或专家同质化时自动触发干预
- **Benchmark 设计的改进**：现有 benchmark 无法区分"真正有分工的 MoE"和"伪 MoE"，需要设计**领域选择性测试集**
- **多模态 MoE 的特殊评估**：需要按模态分别评估专家利用率，确保图像/文本/音频专家都有足够的训练信号

#### 5. 是否针对 RL 场景下的 MoE 模型做过相关优化？

- 这道题与第四章第 2 题有重叠，这里从**更偏工程实践**的角度补充。在实际的 RL + MoE 训练中，优化工作可以分为"训练前"、"训练中"、"训练后"三个阶段。训练前最重要的是**模型初始化策略**——如果从预训练 checkpoint 开始 RL，路由网络已经有一定的分工模式，RL 阶段应该尽量保持这种分工而非重新学习。训练中最大的痛点是**rollout 和 training 的效率不对称**：rollout 是 decode-heavy（逐 token 生成），training 是 prefill-heavy（整个序列一次前向），两者对 GPU 的需求完全不同，需要**异构调度**。训练后的关键是**路由模式的固化与验证**——RL 训练完成后，需要在多种输入上验证路由分布是否仍然健康，避免"训练时看起来正常，部署后遇到 OOD 输入就坍塌"。
- **训练前：初始化与预热策略**
- **从 SFT checkpoint 继承路由模式**：RL 通常在 SFT 之后进行，此时路由网络已经学到了初步的分工模式
- **路由网络 warmup**：RL 前 100 步冻结路由网络，只更新专家参数，让专家先适应 RL 的梯度分布
- **KL 惩罚的初始设置**：初始 KL 系数设大（如 0.1），限制策略偏离 SFT 太远，保护路由模式
- **专家参数的差异化初始化**：如果从头训练，确保不同专家的初始化有足够的随机性差异
- **训练中：效率与稳定性的平衡**
- **Rollout 效率优化**：
  - 使用 vLLM 的 PagedAttention 管理 KV Cache，避免显存碎片
  - GRPO 中同一 prompt 的多个 rollout 共享 prefix KV Cache（**前缀缓存**）
  - 动态 batching：不同长度的生成请求混合组 batch，减少 padding 浪费
- **Training 效率优化**：
  - 使用 FlashAttention + DeepEP 的 fused kernel
  - 梯度累积：多个 rollout batch 的梯度累积后一次更新，减少通信频率
- **稳定性保障**：
  - 路由熵监控 + 自动告警（阈值：$H < \log K + 0.3$）
  - 专家利用率监控 + 自动干预（利用率 < 0.05 的专家触发"唤醒"）
  - 梯度 norm 监控：路由网络的梯度 norm 突然增大通常是路由坍塌的前兆
- **训练后：验证与部署**
- **路由健康度验证**：在多种 OOD（Out-of-Distribution）输入上测试路由分布，确保不会遇到新输入就坍塌
- **专家消融测试**：去掉每个专家后测试性能，确认没有"死专家"
- **压力测试**：ICML 2026 的 RepetitionCurse 工作表明，**重复 token 输入可以触发路由坍塌**，需要在部署前做对抗性测试
- **路由模式的版本管理**：将 RL 训练后的路由模式保存为"快照"，如果部署后发现退化，可以快速回滚
- **工具链与框架选型**
- **veRL（字节跳动）**：原生支持 MoE 的 RL 训练，内置路由监控
- **OpenRLHF**：支持专家并行，但 MoE 路由优化需要自行实现
- **DeepEP + vLLM**：推理侧的标准组合，支持 EPLB 和 PagedAttention
- 实践经验：**框架选型比算法优化更重要**——一个不支持路由重放的框架，再好的算法也跑不起来

#### 6. 在 RL + MoE 的训练场景下，是否碰到过 reward 信号引导路由产生偏差的问题？当时采取了什么应对措施？

- 这道题与第四章第 1 题高度相关，这里从**具体案例和应对细节**的角度展开。reward 引导路由偏差的典型表现是：模型发现"只要把 token 路由到专家 A 和 B，就能得到高 reward"，于是策略梯度不断强化这种路由模式，最终 90% 的 token 都涌向 A 和 B。这个问题在**数学推理和代码生成**任务中尤其严重，因为这两类任务的 reward 信号非常稀疏（要么对要么错），模型倾向于"走捷径"——反复使用已经能产出正确答案的专家组合，而不是探索新的路由模式。我们采取的应对措施是一个**多层防御体系**：第一层是 R3 路由重放保证训练-推理一致性；第二层是轻量 load balancing loss 作为安全网；第三层是路由熵奖励鼓励探索；第四层是定期专家唤醒防止休眠。
- **问题的具体表现与诊断**
- **典型症状**：RL 训练 500 步后，reward 曲线仍在上升，但路由熵从 $\log 8 \approx 2.08$ 降到 0.7（接近 $\log 2$，即只有 2 个专家被使用）
- **诊断方法**：
  - 画出每个专家每 50 步的利用率曲线，观察是否出现"断崖式下降"
  - 对比 RL 前后路由矩阵的热力图，看是否从"块状结构"退化为"单列高亮"
  - 检查生成多样性（distinct-4）：如果路由坍塌，生成内容也会变得单调
- **根因定位**：通常是 reward 函数中某个特定模式（如"使用特定模板"）与某几个专家强相关，RL 放大了这种相关性
- **多层防御体系**
- **第一层：R3 路由重放**
  - 在 rollout 阶段记录路由决策，training 阶段重放
  - 效果：消除训练-推理不一致，但不能阻止 reward 驱动的路由偏移
- **第二层：轻量 Load Balancing Loss**
  - 系数设为预训练阶段的 1/10（如 0.001），作为"安全网"
  - 关键：不能设太大，否则会**与 reward 信号冲突**，导致训练不稳定
- **第三层：路由熵奖励**
  - $r_{\text{total}} = r_{\text{task}} + \beta \cdot H(\text{routing})$，$\beta$ 通常取 0.01~0.05
  - 鼓励路由保持多样性，但不会强制均匀（保留自然分工）
- **第四层：定期专家唤醒**
  - 每 200 步检查一次，利用率 < 0.05 的专家触发"唤醒"
  - 唤醒方式：在下一个 batch 中，强制将 5% 的 token 路由到该专家
  - 同时对休眠专家施加 L2 正则化（$\lambda = 0.01$），防止参数偏离太远
- **Reward 函数的设计改进**
- **避免过于稀疏的 reward**：将 binary reward（对/错）改为 continuous reward（部分正确也给分），减少"走捷径"的动机
- **Process Reward Model（PRM）**：不仅奖励最终答案，还奖励中间推理步骤，让 reward 信号更密集、更均匀
- **Reward 归一化**：对 reward 做 running mean/std 归一化，防止某些任务的 reward 量级远大于其他任务
- **领域均衡采样**：在 RL 的 prompt 采样中，确保不同领域（数学/代码/语言）的比例均衡，避免某类任务主导路由学习
- **经验教训与最佳实践**
- **最重要的教训**：RL 阶段的 MoE 训练，**路由监控的重要性不亚于 reward 监控**
- **学习率分离**：路由网络 lr = 专家网络 lr × 0.2，让路由"慢变"
- **Early stopping on routing entropy**：如果路由熵降到阈值以下，即使 reward 还在上升，也应该停止训练并检查
- **A/B 测试**：在相同 reward 下，比较"有路由约束"和"无路由约束"的生成质量，通常前者在 OOD 测试上更鲁棒
- **长期观察**：路由退化可能在训练后期（数千步后）才显现，**不要因为前几百步正常就放松警惕**
