GQA 的多个 Query 头怎样共享 KV？

理解 GQA，可以先记住一句话：减少的是 KV 头，不是 Query 头。 多个 Query 头读取相同的 Key 和 Value，但仍然各自计算注意力。

这篇只解释头的对应关系和缓存大小。因果 Mask、代码实现与增量推理，接着读手写 GQA。

从八个 Query 头、两个 KV 头说起

假设一层 Attention 有 8 个 Query 头。使用 MHA 时，会为它们准备 8 个 Key 头和 8 个 Value 头，每个 Query 头各用一套 K/V。

改成 2 个 KV 头的 GQA 后，Query 头仍有 8 个，只是每 4 个头共用一套 K/V：

Query 头 对应的 Key / Value
Q0、Q1、Q2、Q3 K0、V0
Q4、Q5、Q6、Q7 K1、V1

这里的“共用”发生在读取数据时。Q0 和 Q1 都拿 K0 来计算分数，再用各自的注意力权重对 V0 加权。它们不需要读取对方的分数或输出。

同一份 K/V，不意味着同一份注意力。 Query 不同，就可能对相同的历史 Token 给出不同权重。

共享输入，为什么输出还能不同？

用一个只有两个历史 Token 的例子来看。把每头维度暂时设为 1，忽略 Mask。共享的 Key 为 [1, 0]，Value 为 [10, 20]。

如果 Q0 的 Query 是 1，它算出的分数就是 [1, 0]。经过 Softmax，两个位置的权重约为 [0.731, 0.269]，输出约为 12.69。

如果 Q1 的 Query 是 −1，分数变成 [−1, 0]，权重约为 [0.269, 0.731]，输出约为 17.31。

两次读取的 K/V 完全相同，但 Query 改变了权重，也改变了结果。维度为 1 时，缩放因子恰好为 1；实际模型会使用更高的头维度。

少了 KV 头，具体省在哪里？

推理时需要保留每层历史 Token 的 K/V，供后续 Query 查询。若每头维度、上下文长度和数据精度相同，KV 头数越少，需要保存的元素就越少。

例如，一条长度为 4096 的序列，每头维度为 128，K/V 都使用 FP16，每个元素占 2 字节。只计算这一层的理想缓存数据量：

Attention 结构 KV 头数 K 和 V 合计
MHA 8 16 MiB
GQA 2 4 MiB

这个例子里，GQA 的缓存是 MHA 的四分之一。这里没有计入分页元数据、分配粒度和临时 Buffer；若计算整个模型，还要考虑层数、请求数及各层实际结构。

但 8 个 Query 头仍然要计算各自的注意力。缓存少了四倍，不能直接推断算力需求或端到端延迟也减少四倍。实际速度还要看 Kernel 是否有效复用共享 KV，以及当前负载的瓶颈。

写教学代码时，可以通过 repeat_interleave 把共享 KV 展开，让普通矩阵乘法直接完成对应计算。长期缓存仍应保存原来的 2 个 KV 头；高效实现可以直接访问共享 KV，不必先复制成 8 个头。

复习时，可以检查这两个问题

共享 K/V 的 Query 头，Attention 输出一定相同吗？

不一定。它们的 Query 通常不同，对同一组 Key 算出的分数和概率也可以不同。

GQA 的共享会要求各个 Query 头串行计算吗？

不会仅因共享只读 K/V 就引入这样的先后依赖。数学上的可并行与 GPU 上的实际吞吐还需区分，详见MHA 各头的独立性。
