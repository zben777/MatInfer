# 右上：RMSNorm
这块完全可以仿你参考图的公式框。

$ r=\sqrt{\frac{1}{n}\sum_{i=1}^{n}x_i^2+\epsilon} $

$ \operatorname{RMSNorm}(x)=\gamma\frac{x}{r} $

旁边只放四个重点：

```latex
① 不计算 mean
② Pre-Norm 结构
③ Reduction + Elementwise
④ 推理中通常偏 Memory-Bound
```

再放一个面试小框：

> **为什么 LLM 越来越多使用 RMSNorm，而不是 LayerNorm？**
>

这就是我们的统一原则：

**公式 + 作用 + 性能特征 + 面试追问。**

# 右侧：Attention 数学
这块继续保留经典公式，因为后面算子层还会继续展开。

$ S=\frac{QK^T}{\sqrt{d}} $

$ P=\operatorname{softmax}(S) $

$ O=PV $

旁边加两个阶段：

### Prefill
```latex
Q: 多 Token
K/V: 多 Token

大矩阵计算
更容易利用 Tensor Core
```

### Decode
```latex
Q: 新 Token
K/V: 全部历史 Token

Q 很短
KV 很长
更容易受 Memory Bandwidth 限制
```

这一小框特别重要，因为我们之后进入算子层就可以直接从这里接：

```latex
Attention
   ↓
Decode Attention
   ↓
Memory Bound
   ↓
FlashMLA / Quantized KV
```

# 四、Continuous Batching
这块应该做成明显的对比图。

## Static Batching
```latex
Time ─────────────────────────→

A ████████████████████
B ███████
C ███████████

B 完成以后：
GPU 仍然要等 A
```

↓

## Continuous Batching
```latex
Time ─────────────────────────→

A ████████████████████
B ███████
          D ██████████
C ███████████
              E █████████
```

旁边大字：

> **请求结束后立即插入新请求，而不是等待整个 Batch 完成。**
>

这时候可以解释它为什么有效：

```latex
Static Batch

有效 batch size
会随着请求完成不断下降

          ↓

Continuous Batch

动态补入请求

          ↓

维持更高 GPU utilization
```

这张小图面试特别好用。

# 五、Prefill 和 Decode
这个模块必须放，因为它是后面很多框架设计的根源。

我建议画成左右对比。

### Prefill
```latex
Prompt:
Token 1
Token 2
Token 3
...
Token N

一次处理大量 Token

特点：
• GEMM 大
• Attention 大
• Compute 更密集
• TTFT 重要
```

### Decode
```latex
历史 Tokens
↓↓↓↓↓↓↓↓↓↓↓

        新 Token Q
             ↓

读取全部历史 KV

特点：
• 每请求通常每轮 1 Token
• KV Cache 读取多
• 小 M GEMM
• Memory / Launch 更敏感
• TPOT / ITL 重要
```

中间放：

```latex
为什么框架要区分 Prefill / Decode？

因为两者：

计算特征不同
访存特征不同
Batch Shape 不同
最优调度策略不同
```

这样后面 PD 分离就自然出现。

# 六、KV Cache Manager
这块应该是第二大的知识块。

核心画：

```latex
Request A
Logical KV blocks

[0][1][2][3][4]
 │  │  │  │  │
 ↓  ↓  ↓  ↓  ↓

Block Table

[17][8][31][4][52]

 │  │   │  │  │
 ↓  ↓   ↓  ↓  ↓

Physical KV Cache

GPU Memory
```

旁边用一句话：

> **逻辑连续，不要求物理连续。**
>

然后解释为什么 Page：

```latex
如果每个请求申请连续大内存：

Request A: 2048 tokens
Request B: 127 tokens
Request C: 4096 tokens

长度动态变化
        ↓
难以连续分配
        ↓
碎片 / 扩容 / 搬迁问题
```

Page 后：

```latex
固定大小 Block
      ↓
按需分配
      ↓
结束立即回收
      ↓
更适合动态请求
```

# 十、Chunked Prefill
这一块非常值得放进去。

假设：

```latex
Request A:
Prompt = 8192 tokens
```

如果一次 Prefill：

```latex
█████████████████████████

占用 GPU 很长时间
```

Decode Request：

```latex
B B B B B B B
```

可能长时间等。

Chunked Prefill：

```latex
A1 A2 A3 A4
```

拆成：

```latex
[A1] → Decode B
[A2] → Decode B
[A3] → Decode B
[A4]
```

旁边写：

> **把超长 Prefill 拆成多个 Chunk，让 Decode 请求有机会穿插执行。**
>

核心 trade-off：

```latex
吞吐
vs
Decode latency
vs
TTFT
```

这非常适合面试。

```latex
 ↓  ↓  ↓  ↓
```

# 十三、PD 分离
PD 值得独立一个小图。

```latex
普通部署：

GPU
├─ Prefill
└─ Decode

相互干扰
```

变成：

```latex
Prefill Pool
GPU GPU GPU
     │
     │ KV transfer
     ↓
Decode Pool
GPU GPU GPU
```

为什么：

```latex
Prefill
更 Compute-heavy

Decode
更 Memory / latency-sensitive
```

所以：

> 可以针对不同 workload 独立扩缩容和调度。
>

注意这里最好不要写成：

> “PD 一定更快。”
>

应该写：

> **PD 引入了 KV 传输和系统复杂度，收益取决于负载与硬件配置。**
>

这会让图显得更专业。

# 三、第一类：GEMM —— 大模型真正的计算核心
这个应该是全图最大的模块之一。

公式：

$ C_{M\times N}
=
A_{M\times K}
B_{K\times N} $

然后不要只写公式，要把 $ M/N/K $ 和 LLM 联系起来。

例如 Linear：

```latex
X: [Tokens, Hidden]
W: [Hidden, Output]
Y: [Tokens, Output]
```

所以：

```latex
M = Token 数 / Batch×Token
K = Hidden Size
N = Output Dimension
```

这个框旁边直接放：

### Prefill GEMM
```latex
M 大
K/N 大

→ 大矩阵
→ Tensor Core 容易吃满
→ 更偏 Compute-bound
```

### Decode GEMM
```latex
M 小
K/N 大

→ Skinny / Small-M GEMM
→ Parallelism 不够
→ Tensor Core 利用率下降
```

这正好接你之前一直讨论的“小 M 大 N/K”。

# 七、Softmax → Online Softmax
这部分可以仿你第一张图那样放公式。

普通稳定 Softmax：

$ m = \max_i x_i $

$ l = \sum_i e^{x_i-m} $

$ p_i = \frac{e^{x_i-m}}{l} $

问题：

```latex
Pass 1：求 max
Pass 2：求 exp + sum
Pass 3：normalize

→ 多次读取数据
```

Online Softmax：

维护两个状态：

$ m_i=\max(m_{i-1},x_i) $

$ l_i
=
l_{i-1}e^{m_{i-1}-m_i}
+
e^{x_i-m_i} $

然后旁边一句大字：

> **核心意义：支持流式 / 分块处理，不需要保存完整 Score Matrix。**
>

这句话比单纯背公式重要得多。

# 十、第三类：RMSNorm / Elementwise
RMSNorm：

$ y_i=
\gamma_i
\frac{x_i}
{\sqrt{\frac{1}{N}\sum_jx_j^2+\epsilon}} $

把它拆成：

```latex
Load x
 ↓
Square
 ↓
Reduction Sum
 ↓
rsqrt
 ↓
Scale
 ↓
Store
```

然后旁边强调：

```latex
计算量小
数据量大

→ Arithmetic Intensity 低
→ 常见 Memory-bound
```

因此优化方向通常：

```latex
Vectorized Load
+
Warp Reduction
+
Fusion
```

而不是一味增加复杂计算。

# 二、中间第一大块：FlashAttention
这一块不能只写“减少 HBM IO”。

应该画出它真正做了什么。

## Naive Attention
```latex
Q × Kᵀ
   ↓
Attention Score
   ↓
写入 HBM
   ↓
读回 Score
   ↓
Softmax
   ↓
写入 HBM
   ↓
```

问题：

---

## FlashAttention
```latex
Q Tile
   │
K Tile ─────┐
            ↓
       QK Tile
            ↓
     Online Softmax
            ↓
V Tile ─→ Partial O
            ↓
      Running m / l / O
            ↓
        Final Output
```

旁边重点：

+ 分 Tile 加载 Q/K/V
+ Score 不完整写回 HBM
+ 使用 Online Softmax
+ Shared Memory / Register 内完成中间计算
+ 提高数据复用
+ 降低 HBM traffic

一句话总结：

> **FlashAttention 的核心不是“Softmax 更快”，而是 IO-aware：重排计算顺序以减少 HBM 访问。**
>


# 八、Alignment

# 十、Bank Conflict
虽然 GPU 层还会再讲，但 Kernel 编程这里要从“程序行为”角度讲一次。



```latex

```


stride=33 后打散。

# 十二、Triton：换了一种编程模型
Triton 这块我建议不要解释成：

> “比 CUDA 简单。”
>

而是：

> **CUDA 以 Thread 为中心；Triton 更偏 Program / Tensor Block 为中心。**
>

CUDA：

```latex
threadIdx.x
blockIdx.x
lane
warp
```

Triton：

```latex
一个 Program Instance
        ↓
处理一块 Tensor
        ↓
tl.arange
tl.load
tl.store
tl.dot
```

比如：

```python

x = tl.load(ptr + offs)
```

你主要思考：

```latex
这个 Program 处理哪一块数据？
```

而不是每个 CUDA thread 的每条指令。

# 十三、CUDA vs Triton 的关键差别
我建议做成一张横向对比：

|  | CUDA | Triton |
| --- | --- | --- |
| 抽象 | Thread / Warp / CTA | Program / Tensor Block |
| Memory | 手动精细控制 | 编译器负责较多映射 |
| Layout | 手动 | DSL / Compiler Layout |
| Tensor Core | WMMA / MMA / CuTe | `tl.dot` 等 |
| 开发效率 | 较低 | 较高 |
| 特殊 bit 操作 | 强 | 视场景 |
| 极致控制 | 强 | 相对少 |
| Autotune | 自己实现较多 | 内置机制方便 |


结论不要写：

> CUDA 一定比 Triton 快。
>

而要写：

> **复杂特殊 Layout / Bit-level / Hardware-specific 场景 CUDA 更灵活；标准 Tensor 算子 Triton 往往能更快达到较高性能。**
>

# 二十二、Barrier 为什么越来越复杂
早期：

```cpp

```

整个 CTA 同步。

但 Producer–Consumer 模型下不希望：

> 所有人每次都停下来。
>

所以现代 Kernel 会大量使用：

+ warp-level sync
+ named barrier / mbarrier
+ async transaction barrier
+ producer-consumer stage state

目标：

> **只同步真正有依赖的线程/阶段。**
>

这就是你项目里“barrier 消减”真正的意义，而不只是：

> 少写一个 `__syncthreads()`。
>

# 三、Warp Scheduler：为什么 GPU 能隐藏延迟
这是非常重要的面试点。

假设：

```latex
Warp 0
load global memory
      ↓
等数据
```

如果 GPU 只能等 Warp 0：

```latex
SM Idle
```

但真实情况：

```latex
Warp 0：等待 HBM
Warp 1：执行 FMA
Warp 2：执行 Load
Warp 3：执行 Tensor Core
```

Scheduler 会切换到：

```latex
Eligible Warp
```

所以：

> **GPU 隐藏延迟主要不是靠单个 Warp 更快，而是靠多个 Warp 之间切换。**
>

这就是 Latency Hiding。

# 四、Eligible Warp / Active Warp / Stalled Warp
这一块建议专门做一个小框。

```latex
Active Warp
=
已经驻留在 SM 上
```

```latex
Eligible Warp
=
当前可以立即发射指令
```

```latex
Stalled Warp
=
因为依赖、内存、同步等暂时不能发射
```

最理想：

```latex
每个 Scheduler 周期
总有 Eligible Warp
```

如果：

```latex
Active Warp 很多
但 Eligible Warp 很少
```

说明：

> Occupancy 看起来很高，但实际 latency hiding 不一定好。
>

这也是为什么：

> **Occupancy ≠ Performance。**
>


还有：

```latex

   ↓

```

但一定写：

> **目标不是 100% Occupancy，而是足够的 latency hiding。**
>

# 十一、Cache Line 和 Memory Transaction
这块一定要分清。

程序层面：

```latex

```

硬件不会一定只去 HBM 拿 4B。

而是按照 cache line / memory sector / transaction 机制处理。

所以：

```latex

        ↓

        ↓
有效 Bandwidth
```

连续：

```latex

...
lane31 A[31]
```

通常能够更高效合并。

随机：

```latex
lane0 A[100]
lane1 A[945]
lane2 A[12]
...
```

可能产生很多 transaction。

# 十二、Coalescing 的硬件本质
这张图可以很直观：

### 好

访问集中。

### 差

一句话：

> **Coalescing 的目标不是“地址必须连续”，而是让 Warp 的内存请求尽量被少量 transaction 覆盖。**

# 十三、HBM
HBM 这一块不要只写“大显存”。


这就把你前面：

> **减少每个 Decode Token 需要从 HBM 搬的数据。**

# 十九、Latency vs Bandwidth
这个区别非常重要。

### Bandwidth Bound
有很多数据传输：

```latex
大量 concurrent loads
```

最终打满 HBM。

### Latency Bound
数据量未必特别大，但：

```latex
等待一次 load
↓
依赖下一步
↓
没有足够其他 warp
```

所以硬件没被打满。

例如：

```latex
Pointer chasing
Random access
Low occupancy
Small workload
```

都可能偏 latency bound。

# 二十、Memory-Level Parallelism
这块很值得放。

GPU 想隐藏 HBM latency，不只是需要 Warp 多。

还需要：

```latex
同时有足够多 outstanding memory requests
```

也就是 Memory-Level Parallelism。

例如：

```latex
Load A
等待
Load B
等待
```

差。

如果能：

```latex
Load A
Load B
Load C
Load D
```

彼此独立：

```latex
MLP ↑
```

更容易隐藏内存延迟。

---

# 二十一、ILP / TLP / MLP
这一张可以非常漂亮地放一个三角：

```latex
               TLP
      Thread-Level Parallelism
              / \
             /   \
            /     \
           /       \
         ILP ----- MLP
Instruction       Memory-Level
Parallelism       Parallelism
```

意义：

### TLP
靠很多 Warp。

### ILP
一个 Warp/Thread 有多个独立指令。

### MLP
同时有多个 outstanding memory requests。

高性能 Kernel 往往是三者的平衡。

# 二十二、Warp Divergence
也需要有一个小框。

```cpp
if (lane < 16)
    A();
else
    B();
```

Warp 内不同线程走不同路径：

```latex
路径 A 执行
路径 B mask 掉

然后

路径 B 执行
路径 A mask 掉
```

于是有效并行度下降。

但要写：

> **不是看到 if 就一定严重，关键看 Warp 内线程是否分歧，以及分支工作量。**
>

# 二十七、怎么判断优化有效
不能只看：

```latex
Kernel ms ↓
```

还要看：

```latex
性能提升来源是不是符合预期？
```

比如你认为：

> vector load 提升带宽。
>

那应该看到：

```latex
instruction count ↓
或
effective bandwidth ↑
```

如果：

```latex
时间变快 5%
```

但对应指标完全没变化，

那可能：

+ noise
+ clock
+ cache
+ benchmark 不稳定

# 二十八、怎么判断“优化到顶”
这一块和第四张 Backend 层呼应，但这里从硬件层做最终判断。

```latex
Memory-bound Kernel

DRAM Bandwidth
已经接近平台可达到值
        ↓
继续减少 arithmetic
基本没价值
```

或者：

```latex
Compute-bound GEMM

Tensor Core utilization
接近高水平
        ↓
MFU 很高
```

再继续：

```latex
Kernel time
已经只占 E2E 5%
```

那么即使再优化：

```latex
Kernel +20%
```

端到端收益也很有限。

这里可以放 Amdahl：

$ S=
\frac{1}
{(1-p)+\frac{p}{s}} $

这很适合解释：

> 为什么 microbenchmark 提升很大，E2E 几乎没变化。
>
